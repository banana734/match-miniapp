## 新增：全页面背景图（房间插画）
- 需求：用户把房间水彩插画放到 `image/home.jpg`，要求「所有页面都当背景」（AskUserQuestion 选定）。
- ⚠️ **踩了个大坑，差点做错**（结论已写进 MEMORY.md）：
  - 第一反应是给全局 `page { background-image: url('/static/x.jpg') }`。实测发现**这条路根本不通**：
    1. 小程序 **WXSS 的 background-image 不支持本地文件路径**（只能用 base64 或网络图）。uni-app 会把路径原样写进 WXSS（`url("static/home-bg.jpg")`），而且 **`dist/dev/mp-weixin/static/` 根本没生成**，图根本没进产物。
    2. 就算能显示，`page` 的 `background-size: cover` 是**按「整页高度」算的**——页面一长（资料表单好几屏），图片会被放大成一团模糊的局部，每个页面糊的程度还不一样。
  - 还试算了 base64 方案（用系统 Python 的 Pillow 压了几档：原尺寸 q65→343KB、1400宽 q72→224KB、1100宽 q75→162KB，base64 后还要 ×1.33），但**因为第 2 条没解决而被否掉**。
- 最终方案：**固定定位的 `<image>` 背景层**
  - 全局样式（common.scss 的 `page{}` 之后）加 `.page-bg { position: fixed; top/right/bottom/left: 0; z-index: -1 }` 和 `.page-bg-img { width/height: 100% }`。
  - `z-index: -1` 是特意选的：排在内容之下；万一某些环境不认负值，失败表现只是「图不显示」，**不会盖住内容**（安全失败）。
  - 15 个页面**每个模板最外层加一行**：`<view class="page-bg"><image class="page-bg-img" src="/static/home-bg.jpg" mode="aspectFill" /></view>`。`mode="aspectFill"` 负责裁剪铺满。
  - 图片放 `src/static/home-bg.jpg`（原图 `image/home.jpg` 保留当源文件）。
- ⚠️ **另一个坑**：`src/static/` 是**这次新建的目录**，**正在跑的 dev watcher 不会扫描到新建的 static 目录**，所以 `dist/dev/mp-weixin/static/` 一直不生成。解决办法：① 手动 `cp` 一份进 `dist/dev/mp-weixin/static/`（本次这么做的，立刻可用）；② 或者重启 `npm run dev:mp-weixin`（全量构建会正确拷贝——已用 `npm run build:mp-weixin` 验证，`dist/build/mp-weixin/static/home-bg.jpg` 728KB 正常生成）。
- 验证：15/15 页面的 `.vue` 各含 1 处背景层；编译后 15/15 的 wxml 都有 page-bg；`app.wxss` 含 `.page-bg`/`.page-bg-img`；`common/assets.js` 里 `_imports_0 = "/static/home-bg.jpg"` 解析正确；dev 产物图片已补齐。

## 微信小程序背景图的三条硬知识（复用）
1. WXSS `background-image` **不支持本地路径** → 要么 base64，要么网络图，要么改用 `<image>` 元素。
2. `page` 的背景 `cover` 按**整页高度**算，不按视口 → 长页面必糊；要「固定壁纸」效果得用 `position: fixed` 的层。
3. 运行中的 dev watcher **不会发现新建的 `src/static` 目录**，新增静态资源目录后要么重启编译进程，要么手动补进 dist。

### ✅ 映射权重规则（2026-09-17 10:42 用户拍板）
用户原话「**同轴就 0.5 映射**」。解读为一条统一规则：**只要映射不是"一个词独占一条轴"，权重就按 0.5 给**。落在两种情况上（两个词共享一轴 / 一个词占两条轴）都适用。

最终导师侧风格 token 权重表：

| 导师选项 | → 家庭轴 | 权重 |
|---|---|---|
| 鼓励启发型 | 启发引导型 | 1.0 |
| 灵活应变型 | 问题向导型 | 1.0 |
| 情感支持型 | 鼓励陪伴型 | **0.5** |
| 耐心倾听型 | 鼓励陪伴型 | **0.5** |
| 结构化引导型 | 系统讲解型 | **0.5** |
| 结构化引导型 | 严格督促型 | **0.5** |

- 家庭侧是恒等映射：选哪个词就落在对应轴上，权重 1.0（有序多选再乘位置衰减）。
- ⚠️ **残留问题（已告知用户）**：`情感支持型` 和 `耐心倾听型` 依然都落在「鼓励陪伴型」轴、权重都是 0.5 → 这两位导师在风格维度**仍然完全同分**，0.5 只是降低了该轴的整体贡献，没有区分开这两个词。
- ⚠️ **余弦副作用（已告知用户）**：权重压到 0.5 会让该导师的向量模长 |A| 变小，而 cos = F·A / (|F|·|A|) → **模长越小反而越占便宜**。所以给 0.5 未必是"降权"。如果需要真正的降权，得改成"分维度加权求和"而不是单一向量的余弦。这点要跟用户确认清楚再动手。

### ✅ 算法结构选定：方案 B —— 分维度余弦 + 加权求和（2026-09-17 10:48 用户回「b」）
用户确认**不用"一个统一大向量算一次余弦"**，改为：

```
总分 = Σ (w_d × cos_d) / Σ w_d        // 归一化到 0~1
cos_d = (a_d · b_d) / (|a_d| × |b_d|)  // 每个维度内部各自算一次余弦
```
- 维度（第一版 3 个）：**科目 / 风格 / 上课方式**。
- 为什么选 B：在单一向量模型里，"映射权重 0.5"会被模长抵消（模长小反而占便宜），
  用户要的"半匹配就老老实实算一半"在 B 里才成立。
- 提议的默认参数（**待用户确认**）：维度权重 科目 0.5 / 风格 0.3 / 方式 0.2；位置衰减 1.0 / 0.6 / 0.3。

  - 导师 A（数学+化学、结构化引导+鼓励启发、线上线下都行）→ 科目 0.735 / 风格 0.910 / 方式 0.707 → **总分 0.782**
  - 导师 B（只会英语、情感支持型、只线下）→ 科目 0.514 / 风格 0 / 方式 0 → **总分 0.257**
  - B 方案下"某维度完全对不上"会实打实拿 0 分并被权重拉低（单一向量模型做不到这点）。

### ✅ 科目维度改用「覆盖率」而非余弦（2026-09-17 10:50 用户回「覆盖率」）
- 原因：科目用余弦时「会得多反而吃亏」——家长只要数学时，只会数学的导师 1.000，会数学+化学的只有 0.857。用户不接受。
- 定义：`科目得分 = 命中的家庭科目权重和 ÷ 家庭全部科目权重和`（**按家长填的顺序加权**，因为家长侧科目是有序的，位置权重 1.0/0.6/0.3）。
  - 分子分母都用家庭侧的权重 → 导师选多选少都不影响，只算"家长的需求被覆盖了几成"。
  - 此时导师会 [数学+化学] 和只会 [数学] 得分相同（都是 0.625），正是用户要的效果。
- 更新后的算例（原例：家长 数学(1.0)+英语(0.6)）：
  - 导师 A（数学+化学）科目覆盖率 = 1.0/1.6 = **0.625** → 总分 = 0.5×0.625 + 0.3×0.910 + 0.2×0.707 = **0.727**
  - 导师 B（只会英语）科目覆盖率 = 0.6/1.6 = **0.375** → 总分 = 0.5×0.375 + 0 + 0 = **0.188**
- ⚠️ **已知副作用（已告知用户，暂不处理）**：覆盖率下**导师把 12 个科目全勾满就永远拿 1.0**。真出问题的话可以把科目改成 **F1**（覆盖率 与 精确率 的调和平均，精确率 = 命中导师科目数 ÷ 导师科目总数），F1 会惩罚"全选"。第一版先按纯覆盖率做，简单优先。
- 最终各维度的算法：
  - **科目** = 覆盖率（加权，按家庭侧权重）
  - **风格** = 余弦（家庭侧恒等映射 + 位置衰减；导师侧按映射表，非独占映射 0.5）
  - **上课方式** = 余弦
- ⚠️ **边界情况：某一侧某个维度没填 → 该维度从总分里剔除、剩余权重重新归一化**（没填 ≠ 不匹配，不该被扣分）；全都没填则总分记 0。
